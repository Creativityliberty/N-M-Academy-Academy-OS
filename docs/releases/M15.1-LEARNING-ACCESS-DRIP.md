# M15.1 — Drip, Prérequis & Unlock Rules

## Goal

Sequence learning without creating a second progress or entitlement system. M15.1 extends the existing Course → Module → Lesson domain and reuses M14 assessments, assignments and completion evidence.

## Canonical model

`course_unlock_rules` stores one condition per target. Targets are `module`, `lesson`, `assessment` or `assignment`. Conditions are `enrollment_delay_days`, `fixed_datetime`, `module_completed`, `lesson_completed`, `assessment_passed` and `assignment_approved`. Multiple enabled conditions on a target are evaluated with AND semantics.

`UnlockRuleDefinitionService` owns authoring validation. It guarantees target/source ownership by the same course, rejects self-dependencies, rejects prerequisites that occur after the target, validates delay/date values and assigns stable positions.

`LearningAccessService` owns runtime evaluation. No React component decides access.

## Entitled vs unlocked

M15.1 intentionally distinguishes two concepts:

- **Entitled** — content included in the student's purchased access rank (`Enrollment.access_rank → Module.minimum_access_rank`).
- **Unlocked now** — entitled content whose drip/prerequisite rules currently pass.

Overall progress and M14.3 completion use tier entitlement so future drip content cannot disappear from the denominator or create an early certificate. Navigation, lesson payloads, Tutor/RAG and interactive learning actions use the current unlock decision.

## Student enforcement

The same access service protects:

- Course Player module/lesson serialization and media redaction;
- lesson progress writes;
- private lesson notes;
- assessment display/submission/scoring;
- assignment display/submission/downloads;
- Tutor lesson scope and course progress context;
- Tutor/RAG retrieval so a future lesson cannot leak through semantic search;
- student MCP `lesson.get` and `learning.progress.get`.

Locked items expose only safe UX metadata: lock state, human-readable reasons and an unlock date when the rule has one.

## Trainer UX

Course Studio adds a separate **Drip & prérequis** workspace instead of inflating the main course editor. Trainers can select a target, choose the condition, select an earlier prerequisite when required, enable/disable rules and remove them.

## Tower / MCP

The governed Academy MCP registry adds:

- `learning.access.rules.list` (READ)
- `learning.access.rules.create` (WRITE)
- `learning.access.rules.update` (WRITE)
- `learning.access.rules.delete` (WRITE)

They call the exact same `UnlockRuleDefinitionService` as Course Studio. Tower remains a client of Academy capabilities rather than owning a second access engine.

## Factory / Coolify

Academy Factory profiles expose `drip` as a Learning capability and generated blueprints emit `ACADEMY_FEATURE_DRIP`. Disabling the feature preserves historical tier access while ignoring M15.1 rule evaluation.

## Non-goals

M15.1 does not introduce cohorts, calendars, teams, agent swarms, a replacement enrollment system, a second progress table or a LessonBlock rewrite.
