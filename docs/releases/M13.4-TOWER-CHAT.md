# M13.4 — Tower Chat / Conversational Control Plane

M13.4 makes Mission Tower conversational. The existing Compiler, governed Mission Runner, Approval Center, Observatory and Evidence Ledger remain the execution primitives; Chat becomes the primary human interface over them.

## Product flow

```text
User message
   ↓
Tower Chat Router
   ├── direct answer from bounded Tower context
   └── Academy action / current private data
            ↓
      Mission Compiler
            ↓
      live MCP validation
            ↓
      Draft mission
            ↓
      Mission Runner
       ├── READ → execute
       ├── WRITE → inline approval
       └── SENSITIVE → exact phrase inline approval
            ↓
      Evidence receipts
            ↓
      grounded chat response
```

Chat never becomes a second authorization system. WRITE/SENSITIVE decisions resume the exact M08 Academy MCP `requestState` through the M13.1 `ApprovalDecisionService`.

## Persistent conversations

Two tables are added:

- `tower_chat_threads`
- `tower_chat_messages`

Messages can reference the compilation, mission, run and approval that produced them. The conversation is therefore inspectable without copying execution state into an unstructured transcript.

## Tower context

The router receives a bounded operational context containing only:

- open Observatory insights;
- pending approvals for the user;
- recent missions.

Current Academy business data that is not already represented by this context must be retrieved through Academy MCP. The model is explicitly instructed not to invent current Academy facts.

## Tool authority

The model does not choose security policy. For actionable requests:

1. Mission Compiler receives the current MCP catalog exposed to the dedicated Tower token.
2. `CompiledMissionValidator` rejects unknown tools and invalid arguments.
3. risk is recomputed from the live MCP `_meta` value, not from model output.
4. `MissionRunner` executes READ and pauses on governed actions.
5. Approval Center resumes the exact MCP approval round.

## Inline approvals

The chat UI renders the real pending `TowerApproval`:

- tool;
- risk;
- arguments;
- expiration;
- exact phrase when required.

Reject stops the governed mission. Approve resumes the existing run. If a later step needs a second approval, Chat surfaces the next approval in the same thread.

## Grounded results

After a completed mission, `TowerChatResponseComposer` receives only the mission results and Evidence receipts. It is instructed not to invent outcomes. Technical secret-like keys are recursively redacted before provider summarization.

## Multi-round provider context

Provider APIs remain stateless at the application boundary. Academy persists the thread and sends only the most recent configured message window to the router. This avoids unlimited conversation growth and works with provider-side prefix caching when available.

Default:

```env
TOWER_CHAT_ENABLED=true
TOWER_CHAT_HISTORY_MESSAGES=16
TOWER_CHAT_MAX_MESSAGE_LENGTH=12000
TOWER_CHAT_AUTO_RUN_READ=true
```

## Security boundary

Never put provider keys, MCP tokens, Stripe secrets, approval requestState or other credentials in chat messages, source code, docs or git. Configure them only through the runtime secret store / Coolify environment.

## Deliberate limits

M13.4 does not bypass the M13.3 static step-argument rule. If a mutation needs an ID that is not known before execution, the compiler must not invent it. Dynamic output binding remains a later Mission Runtime capability.

M13.4 also does not yet make NümFlow/Harness mandatory. Those bridges remain optional and will later extend durable execution/evidence without changing the Chat surface.
