# M14.4.1 — Runtime Launcher & Tower Provisioning Hardening

**Release target:** NÜM Academy OS v1.5.2  
**Date:** 2026-09-02

## Purpose

M14.4.1 is a bounded hardening release between M14 Learning integration and M15 Learning Access. It does not redesign Mission Tower or introduce another runtime. It closes two practical deployment gaps:

1. an Academy Pro Factory blueprint exposed Tower but did not automatically propagate the independent `TOWER_ENABLED` runtime switch;
2. Tower also needs an Academy MCP bearer token backed by a real `academy_mcp_tokens` database record, so setting only the feature/runtime booleans was insufficient for a genuinely ready deployment.

The release also adds a cross-platform one-command local launcher.

## Factory Pro → operational Tower

The Factory relationship is now:

```text
Capability profile: pro
        ↓
tower = true
        ↓
mcp = true
        ↓
ACADEMY_FEATURE_TOWER=true
ACADEMY_FEATURE_MCP=true
TOWER_ENABLED=true
TOWER_ACADEMY_MCP_IN_PROCESS=true
        ↓
random TOWER_ACADEMY_MCP_TOKEN secret
        ↓
academy:bootstrap-instance
        ↓
Mission Tower Bootstrap MCP identity
```

`TOWER_ACADEMY_MCP_TOKEN` is emitted in the Factory **secrets** payload, not the public blueprint environment.

## Bounded bootstrap identity

`TowerBootstrapTokenProvisioner` builds the token abilities from the live `AcademyMcpToolRegistry`:

- READ tools: included;
- WRITE tools: included and still governed by MCP approval;
- SENSITIVE tools: excluded from automatic provisioning;
- tools not permitted for the Academy owner role: excluded.

The identity is named `Mission Tower Bootstrap`.

The bootstrap is idempotent for the same plaintext token. Rotating to a new token revokes the previous active bootstrap token for that owner before creating the replacement.

This keeps the convenience of “Pro → deploy → Tower works” without silently giving the generated token `courses.publish`, `sales.refund`, `certificates.revoke` or other SENSITIVE permissions.

## Runtime Launcher

New root files:

```text
num-academy
num-academy.ps1
num-academy.bat
docker-compose.local.yml
.env.num-academy.example
```

Supported commands:

```text
up
 down
restart
status
logs
doctor
open
help
```

The POSIX launcher and Windows launcher both use the existing production `docker-compose.coolify.yml` plus a tiny local override that maps the application to host port 8080 by default.

No second development topology is created.

## First-run local bootstrap

On first local run the launcher creates gitignored `.env.num-academy` and generates:

```text
APP_KEY
DB_PASSWORD
ACADEMY_BOOTSTRAP_OWNER_EMAIL (default when absent)
ACADEMY_BOOTSTRAP_OWNER_PASSWORD
TOWER_ACADEMY_MCP_TOKEN
```

The default local capability profile is `pro`, specifically so a developer can inspect Community, Events, AI surfaces, Learning Primitives, MCP, Factory integration and Mission Tower from one extracted release. External AI provider keys remain opt-in.

## Existing runtime preserved

The app container still owns:

```text
Nginx
PHP-FPM
Inertia SSR
Laravel queue workers ×2
Laravel scheduler
```

The container entrypoint still performs migrations, bootstrap, cache compilation and missing knowledge reindex before starting Supervisord.

PostgreSQL and Redis remain separate Compose services. Mission Tower remains an application module, not another container.

## Safety invariants retained

M14.4.1 does not change:

- Tower French-by-default behavior;
- Thinking Orbs integration;
- Mission approvals / Evidence;
- the Academy MCP risk model;
- the prohibition on direct `certificates.issue`;
- M14 Assessments / Assignments / Completion / Certificates;
- private assignment storage;
- one-instance-per-client Factory architecture.
