# M14.2 — Assignment & Project Engine

Version: **1.4.0**  
Date: **2026-09-02**

## Purpose

M14.2 adds durable trainer-authored assignments and projects to the existing `Course → Module → Lesson` learning domain without turning submissions into an MCP-controlled grading system and without changing M14.1 assessment semantics.

## Domain

- `CourseAssignment`: assignment/project definition attached to a Course and optionally a Module/Lesson.
- `CourseAssignmentRubricItem`: human-review rubric criterion.
- `CourseAssignmentSubmission`: versioned student submission with status, score and trainer feedback.
- `CourseAssignmentSubmissionFile`: private persisted file metadata.

Supported deliverables remain intentionally bounded: text, URL, files, or mixed submission. M14.2 does not add arbitrary executable uploads or public storage links.

## Private submissions and history

Assignment files use the dedicated private Laravel disk `assignments` rooted at `storage/app/private/assignments`. Coolify persists that directory through the `academy-assignments` volume. Files are downloaded only through authorized controllers; no direct `/storage` URL is emitted.

Each resubmission creates a new version. Trainer review can mark a submission `approved` or `changes_requested` and persists rubric scores plus feedback. Once student history exists, definition changes that would invalidate that history are blocked.

Parent Module/Lesson foreign keys use `RESTRICT` so deleting curriculum structure cannot cascade-delete quiz attempts or assignment submissions. M14.2 also includes an upgrade migration that hardens the M14.1 assessment parent foreign keys.

## Trainer experience

The course-local Assignment workspace supports:

- list/create/update/delete assignment definitions;
- assignment versus project kind;
- deliverable requirements;
- rubric create/update/delete/reorder;
- student submission inspection;
- human rubric scoring and feedback;
- authorized private file downloads.

The existing Course Builder is not replaced; it receives focused links to the learning-primitives workspaces.

## Student experience

The Course Player discovers only assignments available through the existing enrollment/access-rank chain. Students can open an assignment, submit allowed text/URL/files, see the current review status and create a new version when changes are requested.

M14.2 does not automatically complete courses from assignment approval. Completion rules remain M14.3.

## Academy AI / One-Brief

New capability: `assignment.generate`.

Academy AI may propose assignment instructions and a rubric, but it does not grade student work. Materialization still uses Proposal → Apply.

One-Brief-to-Course can enable `generate_assignments`. The durable `assignments` step advances one module assignment at a time so the flow remains resumable and bounded.

## Academy MCP / Mission Tower

Governed definition tools:

- `assignments.list`
- `assignments.get`
- `assignments.create`
- `assignments.update`
- `assignments.delete`
- `assignment.rubric.create`
- `assignment.rubric.update`
- `assignment.rubric.delete`
- `assignment.rubric.reorder`

MCP deliberately does **not** expose a student-submission review tool. Human grading stays inside Academy OS.

## Review Center

M13.9 Course Review Center now displays the assignment/project count and links to the Assignment workspace. Absence of assignments does not block publication in M14.2.

## Mission Tower runtime hardening included

The production fixes reported from the M13.8 deployment were ported selectively to the current codebase:

- portable Inertia page adapters under `resources/js/pages/mission-tower/` instead of a fragile ZIP symlink;
- local in-process Academy MCP fast-path to avoid loopback HTTP deadlocks when Tower points to `${APP_URL}/mcp`;
- `/mcp` CSRF/session exclusion through Laravel application middleware configuration;
- SSR-safe optional chaining for shared `auth` / `academy` props;
- configurable Tower request execution window, default 180 seconds;
- conversation routing focused on the latest user message with no repeated welcome loop;
- Mission Compiler guard requiring category discovery before course creation when `category_id` is unknown;
- rich course-creation planning fields when the MCP schema supports them;
- Tower user-facing answers, compiler titles/reasons and mission summaries are **French by default**, unless the user explicitly requests another language.

Technical MCP tool names, receipt IDs and evidence identifiers stay unchanged for traceability.

## Official Thinking Orbs dependency

`thinking-orbs@^0.3.1` is now a declared frontend dependency. A shared NÜM adapter is used by One-Brief and Mission Tower while preserving the existing business states (`shaping`, `weaving`, `composing`, `listening`, `connecting`, `solving`, `breathing`, `working`, `searching`).

For this release, a normal frontend installation is:

```bash
npm ci
npm run build
```

For an older checkout that predates the dependency declaration, add it first with:

```bash
npm install thinking-orbs@^0.3.1
```

The package install was not fully executable in this local runtime because registry access returned `EAI_AGAIN`; the dependency and lockfile entry are nevertheless part of the release and the normal CI/Coolify path installs them from the registry.

## Explicitly deferred

M14.2 does not add:

- automatic AI grading of open student work;
- completion rules driven by assessment pass / assignment approval;
- certificates;
- public certificate verification.

Those belong to M14.3.
