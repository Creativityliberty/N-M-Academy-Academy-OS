# M13.3 — Mission Compiler

## Goal

Mission Compiler turns a creator's natural-language intent into a safe, reviewable Mission Tower proposal built only from Academy MCP tools currently visible to the dedicated Tower token.

Example:

```text
"Analyse pourquoi mes étudiants décrochent et propose-moi un plan pour les récupérer."
        ↓
Mission Compiler
        ↓
Live MCP catalog
        ↓
Structured proposal
        ↓
Server-side validation
        ↓
Review
        ↓
Apply
        ↓
TowerMission DRAFT
```

Compilation never starts a run automatically.

## Safety model

The AI provider can propose only:

- mission title/objective/summary;
- assumptions;
- tool names;
- JSON arguments;
- a short reason for each step.

The model is **not authoritative** for permissions or risk. After generation, `CompiledMissionValidator`:

1. fetches the live tool catalog through `TowerToolCatalog` / Academy MCP;
2. rejects tools not accessible to the current Tower token;
3. validates every argument against the selected tool `inputSchema`;
4. rejects unknown properties when `additionalProperties=false`;
5. enforces required fields, types, enums, lengths, min/max and basic formats;
6. recomputes `read`, `write` or `sensitive` from the literal MCP `_meta` risk field;
7. derives approval counts and destructive/open-world hints from MCP annotations;
8. enforces `TOWER_MAX_MISSION_STEPS`.

A fake/compromised model output cannot downgrade `sales.refund` or `courses.create` to READ.

## Proposal → Apply

A compilation is stored in `tower_compilations` with:

```text
owner
prompt
provider
model
status
proposal
warnings
error_message
mission_id
applied_at
```

Lifecycle:

```text
compiling
   ↓
proposal ─────→ failed
   ↓
explicit Apply
   ↓
applied
   ↓
TowerMission status = draft
```

Apply uses `lockForUpdate()` and is idempotent: retrying the same Apply returns the already-created mission instead of creating a duplicate.

Before materializing the mission, the stored proposal is validated again against the **current** MCP catalog, so revoked token abilities invalidate a stale proposal.

## Runtime boundary

M13.3 deliberately keeps missions sequential and statically parameterized. The runner does not yet bind an output from step N into step N+1 arguments.

Therefore, when a mutation requires an unknown ID/value, the compiler must not invent one. It should keep that portion analytical/read-only and state what must be reviewed before a follow-up mission. Dynamic step-output binding belongs to a later orchestration milestone.

## AI provider

Mission Compiler uses the existing Tower provider configuration:

```env
TOWER_AI_PROVIDER=inherit
TOWER_AI_MODEL=
```

`inherit` reuses `ACADEMY_AI_PROVIDER` and the corresponding OpenAI/DeepSeek credentials already configured for Academy AI. No duplicate Tower API key is introduced.

## UI

New surface:

```text
/tower/compiler
```

It reuses the Academy shell, Theme Engine and Tower navigation. The proposal preview shows:

- provider/model;
- summary and assumptions;
- READ / WRITE / SENSITIVE counts;
- predicted approval count;
- tool-by-tool reasons and validated arguments;
- destructive/open-world hints;
- explicit Apply to create a draft mission.

Manual mission composition at `/tower/missions` remains available.

## Tests

`tests/Feature/MissionTower/MissionCompilerTest.php` covers:

- live MCP catalog only;
- server-side risk recomputation;
- invented tool rejection;
- invalid tool argument rejection;
- explicit proposal status;
- draft-only Apply;
- idempotent double Apply.

Dependency-backed Laravel/Pest execution remains subject to the release environment having `vendor/` installed.
