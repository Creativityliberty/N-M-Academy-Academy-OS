# M14.3 — Completion Rules + Certificates

**Release target:** NÜM Academy OS v1.5.0  
**Date:** 2026-09-02

## Purpose

M14.3 closes the first Learning Primitives sequence by turning the evidence already owned by the Academy into one canonical course-completion decision and one durable, publicly verifiable certificate. It does not create a second progress system and it does not let Tower or React forge completion.

## Canonical completion evidence

`CourseCompletionService` is the only authority. For the student's actual enrollment tier it evaluates:

1. accessible lessons when `require_all_accessible_lessons` is enabled;
2. enabled M14.1 assessments explicitly marked `is_required_for_completion` and passed at least once;
3. enabled M14.2 assignments explicitly marked `is_required_for_completion` with at least one approved submission.

The access boundary remains:

```text
Enrollment.access_rank
        ↓
Module.minimum_access_rank
        ↓
accessible lessons / assessments / assignments
```

Lesson-scoped primitives use the lesson as the most precise scope; a module ID cannot accidentally make an inaccessible lesson-scoped primitive count for a lower tier.

Completion requires **at least one accessible pedagogical criterion**. A course with zero required lessons, zero required assessments and zero required assignments cannot grant an instant certificate.

## Historical milestone

A successful evaluation creates at most one `CourseCompletion` per course/student. Its `evidence_snapshot` persists:

- enrollment access rank;
- exact requirement counts;
- required/completed lesson IDs;
- required/passed assessment IDs;
- required/approved assignment IDs;
- completion timestamp.

The milestone is historical. Later lesson unmarking or policy edits do not silently erase a completed course.

## Certificates

When enabled by the course policy, completion issues at most one `CourseCertificate`:

- random public UUID verification code;
- recipient name snapshot;
- course title snapshot;
- issuer snapshot;
- certificate title snapshot;
- issued timestamp;
- SHA-256 document hash;
- explicit revocation fields.

No certificate can be issued for an unpublished course. There is no direct `certificates.issue` controller or MCP tool.

## Public verification and PDF

Public verification is intentionally limited to credential-public information:

- recipient name;
- course title;
- issuer;
- certificate title;
- issued date;
- verification code;
- valid/revoked state.

The internal revocation reason, email, payments, quiz answers, rubric scores and assignment content are not exposed publicly.

The PDF is rendered on demand using core PDF Helvetica/WinAnsi encoding. No font file and no generated PDF binary is stored in the release.

## Trainer experience

A course-local **Complétion & certificats** workspace lets the trainer:

- require or ignore all accessible lessons;
- choose required assessments;
- choose required assignments;
- enable/disable future certificate issuance;
- set certificate title and issuer display name;
- inspect completion/certificate counts;
- revoke an issued certificate with a mandatory reason.

The M13.9 Review Center links to this workspace but completion policy is not a course-publication prerequisite.

## Student experience

The Course Player receives a server-computed checklist for:

- lessons completed / required;
- assessments passed / required;
- assignments approved / required;
- completed state;
- certificate verification link when available.

`/student/certificates` lists the student's own credentials with verification, PDF and share links.

## MCP / Mission Tower

M14.3 adds governed tools:

```text
completion.policy.get      READ
completion.policy.update   WRITE
certificates.list          READ / PERSONAL
certificates.get           READ / PERSONAL
certificates.revoke        SENSITIVE / PERSONAL
```

There is deliberately no `certificates.issue` tool. Certificate issuance remains derived from canonical learning evidence.

Mission Tower keeps the M14.2 runtime fixes and speaks French by default. `thinking-orbs@^0.3.1` remains the shared frontend activity dependency for Tower and One-Brief.

## Security hardening found during M14.3 QA

The release also closes four edge cases found before packaging:

- unpublished courses can never complete;
- zero configured pedagogical criteria can never complete;
- inaccessible lesson-scoped assessments/assignments are excluded correctly even when another scope is present;
- public verification no longer exposes the internal revocation reason.

`CourseAssignment.is_required_for_completion` is also part of the canonical mass-assignable model fields.

## Installation / upgrade

Normal application setup remains unchanged:

```bash
composer install --no-interaction --prefer-dist
npm ci
php artisan migrate --force
npm run build:ssr
```

Production/Coolify should use Node 24 as configured by CI. Runtime secrets belong in Coolify/environment variables and are never packaged.

## Local verification limits

In the release-build environment used for this milestone:

- Laravel/Pest and `migrate:fresh` cannot start because `vendor/autoload.php` is absent and Composer is unavailable;
- `npm ci` did not finish within the available probe window and the local runtime is Node 22 while one dependency requires Node 24;
- Docker is unavailable locally.

Those gates are therefore reported as **BLOCKED**, not PASS. The source/static/cumulative contract gates are rerun on fresh ZIP extractions before release.
